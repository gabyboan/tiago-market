Este documento reemplaza como diagnóstico vigente los informes de junio,
julio y 18 de septiembre, que se conservan como antecedentes. Los conteos y
resultados remotos siguientes corresponden a la auditoría de lectura realizada

## Arquitectura y ejecución

Flutter `0.2.2+4` usa Supabase Auth y RPC públicas `nearby_prices_v2`,
`online_prices_v2` y `nearby_branches`. Con la configuración local, categorías
y feedback usan la Edge Function `api` v8. La API Node/Express `0.8.0` permanece
en el repositorio, pero no es equivalente a esa función desplegada. La ingesta
Dart se ejecuta fuera de Flutter: evidencia → NDJSON → staging → snapshots.
Favoritos, historial y lista se guardan localmente, sin sincronización de cuentas.

```bash
cd apps/flutter_app
flutter run -d chrome --dart-define-from-file=dart_defines.local.json
```

La configuración requiere URL y clave pública de Supabase. `API_BASE_URL`
apunta al servicio HTTP, localmente `https://<ref>.supabase.co/functions/v1/api`.
Las claves de servidor quedan fuera de Flutter. Para Node: configurar `.env`
según `.env.example` y ejecutar `npm run api` desde la raíz.
Sin configuración, el cliente actual no garantiza datos demo: puede mostrar
“API no configurada”. Hay lockfiles para Node y Flutter.

## Funcionalidades y bloqueantes

| Funcionalidad | Clasificación y evidencia |
|---|---|
| Invitado, navegación, agrupación por presentación | Verificadas en pruebas locales. |
| RPC de precios y sucursales | Verificadas por HTTP público; no equivale a GPS/UI en dispositivo. |
| Favoritos, historial y operaciones de lista | Pruebas básicas aprobadas; exactitud de estimaciones incompleta. |
| Google Auth, GPS físico, compartir, telemetría | Implementados; sin validación completa en dispositivo en esta auditoría. |
| Filtros/paginación local | Incompletos: categoría/página no llegan a la RPC local; riesgo de repetir las primeras 100 filas. |
| Publicación por negocios / sincronización de listas | Ausentes; vendedor muestra “próximamente”. |
| Android firmado | Incompleto: falta keystore local; GitHub solo tiene `SUPABASE_URL` y `SUPABASE_SERVICE_ROLE_KEY`. |

Correcciones necesarias antes de entregar la app a usuarios (fuera del experimento):

1. Totales: no combinar sucursales de una misma cadena; no sumar alternativas
   de distintas cadenas como costo único. `calculateStoreTotals` agrupa por
   `storeName` y la hoja suma sus totales.
2. Favoritos/lista: conservar evidencia y fecha original; no reconstruir una
   observación `fresh` con la fecha de guardado ni sumar precios vencidos.
3. Calidad: exigir URL de evidencia también en resultados locales. El lote
   Home Depot tiene categorías incorrectas y una escalera presentada como “150 kg”;
   `observation_url` devuelve el SKU aunque el raw payload guarda la URL oficial.
4. Filtros/paginación: respetar categoría y evitar repetir resultados locales.
5. Backend desplegado: validar identidad del feedback y limitar abuso antes de
   ampliar el acceso; reconciliar rutas HTTP y RPC antiguas.

## Seguridad y límites

Las nueve tablas revisadas de `public`/`ingestion` tienen RLS y no conceden
lectura/escritura directa a `anon`/`authenticated`. Los accesos públicos probados
a tablas sensibles y `latest_prices` devolvieron 401. Las cinco RPC públicas
`SECURITY DEFINER` tienen `search_path` vacío; sus contratos requieren revisión:
`online_prices` antigua devolvió 100 observaciones vencidas.

La Edge Function usa `service_role` del lado servidor, pero acepta el `user_id`
del cuerpo del feedback sin verificarlo y carece de rate limit en su código.
El advisor también informa `pg_trgm` en `public` y protección de contraseñas
filtradas desactivada. Los roles buyer/seller del cliente son navegación,
no deben emplearse como autorización confiable del backend.

Auditoría local previa a esta entrega: 49 tests Flutter y 22 Node aprobados;
`flutter analyze`, `npm run build` y `npm run lint` sin errores.
No se verificaron login real, Android conectado, firma release, precio físico
en tienda ni actualización sostenida de fuentes directas. Los tests de parsers
usan fixtures y no demuestran disponibilidad actual de un sitio externo.

El alcance elegido es supermercados, sucursal física y CDMX. Los pagos
informados no fijan alcance ni precio total. Esta entrega no agrega funciones
de usuario: entrega evidencia y veredicto de viabilidad de la primera fuente.
